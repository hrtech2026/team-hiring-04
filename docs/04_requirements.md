# Формализация требований

## User Stories

### US-01. Профиль вакансии из интервью с руководителем

Как рекрутер,
я хочу превратить интервью с руководителем отдела в структурированный профиль
вакансии (обязательные и желательные критерии, навыки, опыт, личные качества,
формат отчёта, сроки),
чтобы критерии отбора были прозрачными и утверждены до запуска скрининга.

Критерии приёмки:

```gherkin
Given интервью с руководителем проведено по шаблону, When рекрутер формирует профиль вакансии, Then профиль содержит обязательные критерии, желательные критерии, формат отчёта и сроки, и ему присвоена версия
Given профиль не утверждён руководителем, When запускается обработка откликов, Then система не принимает отклики в обработку и сообщает, что нужно утверждение (H1)
Given в профиле есть критерий по защищённому признаку (пол, возраст, национальность, семейное положение), When профиль отправляется на утверждение, Then система отклоняет критерий и указывает причину
Given руководитель меняет критерий, When профиль сохраняется, Then создаётся новая версия, а решения по прежним откликам остаются привязаны к старой версии
```

### US-02. Обезличивание и структурирование резюме

Как рекрутер,
я хочу, чтобы резюме перед оценкой моделью автоматически обезличивалось и
приводилось к структуре (опыт, навыки, образование),
чтобы пол, имя, национальность и возраст не влияли на рекомендацию.

Критерии приёмки:

```gherkin
Given отклик с резюме в поддерживаемом формате, When выполняется блок 1, Then в данных для модели нет имени, пола, национальности, контактов, адреса, фото и дат рождения, а годы работы и учёбы заменены стажем
Given имя кандидата упомянуто внутри текста опыта, When выполняется проверка запроса перед отправкой, Then отправка блокируется, а отклик уходит в расширенный разбор (H3)
Given резюме не удалось разобрать (скан без текста, повреждённый файл), When выполняется блок 1, Then отклик помечается «требуется ручной просмотр» и передаётся в H3, а модель не вызывается
Given резюме на английском языке, When выполняется блок 1, Then структурирование выполняется с тем же составом полей
```

### US-03. Сводка и рекомендация advisor с обоснованием

Как рекрутер,
я хочу получать краткую сводку по кандидату с выводом по каждому критерию,
цитатой из резюме и рекомендацией,
чтобы быстро оценить соответствие вакансии и проверить вывод модели.

Критерии приёмки:

```gherkin
Given обезличенный профиль кандидата и утверждённый профиль вакансии, When вызывается advisor, Then сводка содержит вывод по каждому критерию с цитатой из резюме, рекомендацию и уверенность
Given вывод модели не подтверждён цитатой из резюме, When сервис проверяет ответ, Then этот вывод отбрасывается, а при повторной ошибке отклик уходит в H3
Given в резюме скрыт текст с инструкцией для модели, When выполняется проверка содержимого, Then сработавший детектор направляет отклик в H3, а рекомендация не используется
Given языковая модель недоступна, When рекрутер открывает отклик, Then отклик остаётся в очереди, а рекрутер работает вручную без потери данных
```

### US-04. Решение рекрутера с причиной

Как рекрутер,
я хочу принимать решение по каждому кандидату сам и фиксировать причину,
чтобы ответственность была у человека, а основание отказа можно было проверить.

Критерии приёмки:

```gherkin
Given сводка показана, When рекрутер открывает отклик, Then сначала показаны критерии и цитаты, а рекомендация показана отдельным блоком после них
Given рекрутер выбирает «отказать», When он сохраняет решение, Then система требует причину, связанную с критерием профиля, и не сохраняет отказ без причины
Given рекрутер не согласен с рекомендацией, When он принимает другое решение, Then в журнал записывается override_reason
Given срок решения истёк, When рекрутер не дал ответа, Then отправляется напоминание и уведомление HR-лиду, а статус отклика не меняется автоматически
```

### US-05. Эскалация на расширенный разбор

Как рекрутер,
я хочу, чтобы отклики с рисками ошибки попадали на расширенный разбор по
оригиналу резюме,
чтобы спорные и «пограничные» кандидаты не терялись из-за модели.

Критерии приёмки:

```gherkin
Given рекомендация «не соответствует» по обязательному критерию, When сервис проверяет триггеры, Then отклик направляется в H3, а рекрутеру доступен оригинал резюме
Given уверенность модели ниже порога, When сервис проверяет триггеры, Then отклик направляется в H3
Given отказ в H3, When решение сохраняется, Then для отказа требуется подтверждение второго проверяющего или HR-лида при расхождении
Given отклик попал в контрольную выборку, When сервис маршрутизирует отклик, Then он направляется в H3 независимо от рекомендации
```

### US-06. Журнал решений

Как HR-лид и аудитор,
я хочу видеть журнал решений с версией промта и профиля вакансии и хешем входных данных,
чтобы воспроизвести любое решение и проверить его основание.

Критерии приёмки:

```gherkin
Given принято любое решение по кандидату, When оно сохраняется, Then в журнале есть запись со всеми полями из 03 (decision_id, timestamp, actor_id, system_version, input_hash и другие)
Given запись в журнале существует, When кто-либо пытается изменить или удалить её, Then операция отклоняется, допустима только дозапись
Given по input_hash запрошено воспроизведение решения, When аудитор запускает повторный расчёт на тех же обезличенных данных и версиях, Then результат совпадает с записью в пределах допуска повторных запусков модели
```

### US-07. Проверка на скрытые признаки

Как HR-лид,
я хочу запускать парные тесты на резюме с изменёнными именем, полом и возрастом,
чтобы убедиться, что эти признаки не влияют на рекомендации.

Критерии приёмки:

```gherkin
Given набор пар резюме, различающихся только именем, полом или возрастом, When выполняется парный тест, Then доля пар с разной рекомендацией не превышает целевого значения (≤5%)
Given доля расхождений выше целевой, When тест завершён, Then версия промта или модели помечается как не допущенная к использованию, а HR-лид получает отчёт
Given изменилась версия промта или модели, When новая версия готовится к использованию, Then парный тест и регрессионный набор запускаются до включения версии
```

## Use Cases

### UC-01. Первичный скрининг одного отклика

| Поле | Значение |
|---|---|
| Актёры | Рекрутер; сервис скрининга; ИИ-advisor (внешняя модель); HR-лид (при эскалации) |
| Предусловия | Профиль вакансии утверждён (H1); рекрутер авторизован; отклик получен и сохранён |
| Триггер | Новый отклик поступил в очередь обработки |

Основной сценарий:

1. Сервис получает резюме и сохраняет оригинал во внутреннем хранилище.
2. Блок 1 извлекает опыт, навыки, образование, маскирует имя, пол, национальность, контакты, адрес, фото и даты рождения, заменяет даты стажем.
3. Сервис проверяет полноту извлечения и отсутствие ПДн в исходящем запросе.
4. ИИ-advisor получает обезличенный профиль и профиль вакансии и возвращает сводку: вывод по критериям с цитатами, рекомендацию, уверенность.
5. Сервис проверяет цитаты и триггеры эскалации; триггеров нет, сводка показывается рекрутеру (H2).
6. Рекрутер читает критерии и цитаты, затем рекомендацию, и выбирает: пригласить, запросить данные или отказать с причиной по критерию.
7. Сервис записывает решение в decision_log.
8. Сервис обновляет статус отклика; общение с кандидатом выполняет рекрутер вне системы.

Альтернативные сценарии:

| # | Условие | Реакция |
|---|---|---|
| 5a | Сработал триггер эскалации (рекомендация «не соответствует» по обязательному критерию, низкая уверенность, неполные данные, подозрительный контент, контрольная выборка) | Отклик направляется в H3: рекрутер видит оригинал, при отказе нужен второй проверяющий |
| 5b | Рекрутер не ответил в срок | Напоминание, затем уведомление HR-лиду; автоотказа и автоприглашения нет |
| 6a | Рекрутер не согласен с рекомендацией | Принимает своё решение, указывает override_reason, запись попадает в журнал |
| 6b | Рекрутер выбирает «отказать» без причины | Система не сохраняет решение, требует причину по критерию профиля |

Исключения:

| # | Ошибка | Реакция |
|---|---|---|
| 2b | Резюме не читается (скан без текста, повреждённый файл) | Отклик помечается «требуется ручной просмотр», уходит в H3, модель не вызывается |
| 3b | В исходящем запросе найдены ПДн | Отправка блокируется, инцидент пишется в журнал, отклик уходит в H3 |
| 4b | Модель недоступна или превышено время ответа | Один повтор; затем отклик остаётся в очереди для ручной работы, ничего не отклоняется |
| 4c | Ответ модели в неверном формате или без цитат | Ответ отбрасывается, один повтор; при повторной ошибке отклик уходит в H3 |

Постусловия: по отклику есть решение человека и запись в decision_log;
оригинал резюме и персональные данные не покидали внутренний контур.

## Нефункциональные требования

| Категория | Требование | Проверяемость |
|---|---|---|
| Производительность | Сводка по одному отклику готова не позднее 60 секунд (стартовое значение); пачка из 61 отклика обрабатывается не более 30 минут | Замер на тестовом наборе резюме, 95-й процентиль времени |
| Надёжность | При недоступности модели процесс не блокируется, отклики остаются в очереди для ручной работы; ни один отклик не теряется | Тест отказа модели; сверка: поступившие = обработанные + в очереди |
| Безопасность | Оригиналы резюме доступны только рекрутеру и HR-лиду; ключи доступа к модели хранятся в защищённом хранилище; журнал только дозапись | Ревью прав по ролям, тест на попытку изменения журнала |
| Приватность | ПДн не попадают во внешний контур: в исходящих запросах нет имён, телефонов, email, адресов, дат рождения | Автоматический поиск ПДн в 100% исходящих запросов тестового набора, выборочная проверка в работе |
| Объяснимость | Каждая рекомендация содержит вывод по каждому критерию с цитатой из резюме и версией профиля | Выходная проверка: доля выводов с подтверждённой цитатой равна 100%; чтение 20 случайных сводок командой |
| Аудит | Решение по каждому отклику записано в decision_log (поля из 03), воспроизводимо по input_hash | Воспроизведение 10 случайных решений; сверка числа решений и записей |
| Локализация | Резюме на русском и английском; интерфейс и сводка на русском; корректная обработка кириллицы и форматов дат | Тестовые резюме на двух языках, проверка вывода |
| Сопровождаемость | Системный промт, профиль вакансии и пороги версионируются; смена версии запускает регрессионный набор и парные тесты | Проверка, что запуск версии без пройденных тестов невозможен |

## Ограничения и допущения

Ограничения — не обсуждаются, это внешние данные.

| Ограничение | Источник |
|---|---|
| Обработка персональных данных кандидатов должна соответствовать закону о персональных данных (152-ФЗ), включая условия передачи данных за пределы компании | Законодательство РФ (формулировку и применимость подтвердить у юриста) |
| Запрет дискриминации при найме и необоснованного отказа в заключении трудового договора | Трудовой кодекс РФ, ст. 3 и ст. 64 (сверить с актуальной редакцией у юриста) |
| Для отказа в найме уровень автоматизации не выше L1; финальное решение за человеком | Методические указания практики и принципы TO-BE |
| Валидация результата со стороны HR и собеседования, оценка софт-скиллов вне зоны ответственности проекта | Постановка практики |

Допущения — проверяемы, подтверждение меняет архитектуру.

| Допущение | Кто подтвердит | Что меняется, если неверно |
|---|---|---|
| Руководитель отдела может описать требования в интервью до проверяемого профиля | Рекрутер и руководитель отдела на пробном интервью | Нужны типовые профили вакансий и более строгий шаблон интервью (US-01) |
| Обезличивание убирает прямые идентификаторы без потери смысла | Команда: парный тест | Меняется перечень передаваемых полей (US-02, R1) |
| Рекрутер не принимает рекомендацию автоматически | Команда: метрики журнала в тестовом прогоне | Меняется показ рекомендации, усиливается эскалация (US-04, R4) |
| Стартовые пороги (уверенность 0,7, контрольная выборка 10%, сроки 2–3 дня) пригодны | Команда: тестовый прогон на 100+ вакансиях | Пересчитываем пороги и нагрузку на H3 |
| Передача обезличенных данных во внешнюю модель допустима по политике компании | Юрист или ответственный за ПДн | Переходим на модель во внутреннем контуре (граница данных в 03) |
| Среднее 61 отклик на вакансию применимо к целевой компании | Рекрутер: фактические данные по вакансиям | Пересчитываем время и нагрузку (NFR производительности) |

## Definition of Ready

- [ ] Пользователь и его роль определены
- [ ] Ценность описана в одну фразу
- [ ] Критерии приёмки сформулированы и проверяемы
- [ ] Зависимости от других историй перечислены
- [ ] Уровень автоматизации выбран и согласован с TO-BE
- [ ] Понятно, где история создаёт риск для человека

## Definition of Done

- [ ] Реализация проходит все критерии приёмки
- [ ] Для L1 и выше существует лог решения с объяснением
- [ ] Есть тест на граничные и ошибочные сценарии
- [ ] Права доступа настроены по ролям
- [ ] Документация для пользователя обновлена
- [ ] История просмотрена другим членом команды
- [ ] Риски ИИ для этой истории перепроверены, контрмеры работают
